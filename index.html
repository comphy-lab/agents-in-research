You are at the centre.

Use these rings as a teaching model: each layer answers a different question about what we casually call “the agent”. The boundary is conceptual, rather than a network diagram.

Interface · where you type and read
A chat website, desktop app, command-line interface (CLI), editor or T3 Code. T3 provides one interface to multiple coding agents; it uses their existing harnesses. [1]
Harness · where actions happen
Think of an agent loop given context, tools, a shell and a machine. Claude Code, Codex and compatible ACP agents are examples. T3 integrates through SDKs, app servers or ACP, depending on the agent. ACP standardises communication between agent clients and agents. [1] [2]
API / access · who can call the model
This ring groups provider access and authentication: a supported subscription login or API credentials. Authenticate the agent on the machine running its harness; the laptop’s T3 login links environments separately. [3] [11]
Models · the remote inference layer
In this picture, models run on GPUs in a data centre. Hosting the harness on your workstation does not make model inference local: prompts and code still go to the selected model provider. [8]

A loop, with a stopping condition.

A useful working picture of a coding agent is a repeated cycle. Define the check before handing over the task.

  1. Read contextTask, files and instructions.
  2. PlanChoose the next action.
  3. ActEdit a file or run a command.
  4. ObserveRead the output and errors.
  5. Repeat or stopUntil the check passes, or the agent gives up.

Teaching schematic, not a promise that every harness follows these steps in this order. For research, choose a check that tests the scientific claim as well as whether the code runs.

A sandbox you control

A spare Linux workstation or laptop is a practical place to start. The following is a recommended setup, rather than a claim that a dedicated account provides complete isolation.

Keep the working surface small

  • Provide power and a reliable internet connection. Keep the workstation running and reachable while you use it remotely. [5]
  • Create a dedicated user account. Keep personal credentials out; add only the scoped provider and project logins the agent needs.
  • Restrict outbound SSH from that account where practical. Blocking port 22 is a speed bump, not a full sandbox; do not treat a port rule as a complete security boundary.
  • Keep normal HTTPS available for package installs and provider access. Optional SSH from your laptop to the workstation is useful for setup and maintenance.

Size for the work

Claude Code documents a 4 GB+ RAM baseline. The reviewed T3 documentation does not publish a combined minimum for T3, the harness and your project tools. [4]

As starting advice, consider 8–16 GB for a modest workload, then size for your builds, browsers, datasets and concurrent agents. This is advice, not a T3 requirement or a measured capacity guarantee.

For the background-service recipe below, Linux needs systemd user services. Setup enables lingering so the service can start at boot and survive logout; follow its recovery instructions if administrator permission is needed. [6]

Install on the workstation.
Control from your laptop.

These commands follow the cited T3 documentation snapshot. They are installation instructions, not a report of an installation tested for this page. Read the installer before running it.

  1. Install T3 on the Linux workstation

    Run as the dedicated user. The documented installer puts t3 in ~/.local/bin; follow its PATH instructions if needed. [7]

    curl -fsSL https://t3.codes/install.sh | sh

  2. Start the server and choose T3 Connect

    t3 up

    Choose Connect and sign in. When setting up over SSH, open the displayed browser link on another device, check the short code and approve. Connect runs T3 as a background service. [5]

    Check the environment and service state: [6]

    t3 status
t3 service status

  3. Install and authenticate your agent there

    Use the agent’s official installation guide, then run the matching login command on the workstation before starting a thread. Choose the provider you intend to use. [3]

    Claude Code, once installed

    claude auth login

    Codex CLI, once installed

    codex login

    T3’s Codex provider also offers Connect with ChatGPT, including installation, on the selected remote environment. [3]

  4. Install the laptop client, or use the web app

    Choose one route from the official downloads. [7]

    macOS

    brew install --cask t3-code

    Windows

    winget install T3Tools.T3Code

    Debian / Ubuntu desktop

    Download the matching release .deb, then:

    sudo apt install ./T3-Code-*.deb

    Browser

    Open app.t3.codes. No desktop installation is needed. [7]

  5. Sign into the same Connect account

    In the laptop client, sign into the same account used on the workstation and select that environment. Agent installation and provider authentication belong to the selected workstation. [5] [3]

Documentation scope: T3 main-branch snapshot b78914e, reviewed 17 November 2026. Some source-documented features may differ in stable client releases.

Remote control has a route.

Separate where commands execute from how prompts and approvals reach that machine.

Control paths described by the official sources
ConnectionExecution and message path
Claude Remote ControlClaude Code runs on your machine. Anthropic routes messages between clients and the local session through its API over TLS; the synchronised transcript, including tool activity, is stored on Anthropic servers. [9]
ChatGPT / Codex remote connectionsThe mobile/desktop remote-control route is vendor-mediated: the phone sends prompts and approvals to ChatGPT while commands execute on the connected, awake Mac or Windows host. The cited guide describes a secure relay but does not establish every network hop or a complete retention policy. [9]
Codex SSH / CloudSSH is a separate route: the desktop app manages a remote Codex App Server through SSH. Codex Cloud instead executes tasks on OpenAI-managed computers. Do not apply the mobile relay description to both. [9] [10]
T3 ConnectAgents run on your workstation. T3-managed Cloudflare tunnels carry application traffic. A T3 relay provisions and discovers endpoints and brokers credentials; ordinary HTTP/WebSocket traffic uses the environment’s tunnel hostname rather than passing through the relay Worker. [8]

Managed Connect

Free for now, for up to three linked machines per account. Phones and browsers do not count towards that allowance. This is the documented offer as of 17 November 2026. [5]

Your own Connect infrastructure

The source and runbooks support an operator deployment using your own Cloudflare, Clerk, database and related services, plus client configuration or rebuilding. The reviewed docs do not provide a turnkey, entirely independent Linux-only setup. [12]

The tunnel does not move inference onto your workstation. Whatever connection you choose, prompts and code still go from the workstation to the selected model provider. [8]

Subscription or pay per token?

A subscription buys plan access

Subscriptions can be much cheaper for heavy interactive use than pricing the same recorded tokens at API list rates. That comparison is an estimate, not a guaranteed API allowance or a measure of the provider’s compute cost. OpenAI explicitly separates API token prices from subscription usage. [11] [13]

The API bills usage

API list prices charge input and output tokens separately. Cache accounting, tools and service tiers can change the bill. Compare against the provider’s current rates and your actual workload. [11]

Some plans also include claimable API credits under separate rules; for example, Claude Max and Ultra document these allowances. Do not confuse those credits with an API-equivalent estimate of subscription use. [14]

Keep shared HPC behind a narrow door.

Recommended practice: prepare the submission package locally, then use small submit and status scripts you have read and approved. Give the agent only the permissions those steps need, within your centre’s policies.

  1. Prepare: review the code, job script, inputs and requested resources.
  2. Submit: use the approved script for the intended job and record the scheduler job ID.
  3. Poll: read status and logs for that job. Automatic polling is optional; keep it bounded and appropriate for the service.

This is a workflow recommendation. Submission and polling scripts belong in a separate repository; this guide does not provide cluster access or scripts.
