The layers

You are at the centre.

Use these rings as a teaching model: each layer answers a different question about what we casually call “the agent”. The boundary is conceptual, rather than a network diagram.

Interface Where you type and read
A chat website, desktop app, command-line interface (CLI), editor or T3 Code. T3 provides one interface to multiple coding agents; it uses their existing harnesses. [1]
Harness Where actions happen
Think of an agent loop given context, tools, a shell and a machine. Claude Code, Codex and Antigravity are examples, as are other ACP-compatible agents. T3 integrates through SDKs, app servers, ACP or a CLI, depending on the agent. ACP standardises communication between agent clients and agents. [1] [2]
API / access Who can call the model
This ring groups provider access and authentication: a supported subscription login or API credentials. Authenticate the agent on the machine running its harness; the laptop’s T3 login links environments separately. [3] [11]
Models The remote inference layer
In this picture, models run on GPUs in a data centre. Hosting the harness on your workstation does not make model inference local: prompts and code still go to the selected model provider. [8]

The setup in this guide

You type in T3 Code on a laptop, phone or browser. The T3 server, the harness, its shell and your code live on your own Linux workstation. The harness calls the model through your subscription or API key, and inference runs on the provider’s GPUs. [8]

A chat website

On a site such as chatgpt.com, interface, harness, machine and GPUs all sit in one company’s cloud. That is convenient, but the provider decides what the agent’s machine can reach; your workstation, data and simulations take part only through uploads or the integrations you authorise.

The loop

A loop, with a stopping condition.

A useful working picture of a coding agent is a repeated cycle. Define the check before handing over the task.

  1. Read contextTask, files and instructions.
  2. PlanChoose the next action.
  3. ActEdit a file or run a command.
  4. ObserveRead the output and errors.
  5. Repeat or stopUntil the check passes, or the agent gives up.

Teaching schematic, not a promise that every harness follows these steps in this order. A chat thread on a website is an agent in this sense too; a harness gives the same loop a shell, files and a machine. For research, choose a check that tests the scientific claim as well as whether the code runs.

Your workstation

A sandbox you control

A spare Linux workstation or laptop, old or new, is a practical place to start. The following is a recommended setup, rather than a claim that a dedicated account provides complete isolation.

Why limit what it can reach

Recent reports, each read on the outlet’s own page: Anthropic said its Claude models gained unauthorised access to other organisations’ systems during safety tests (CNBC, 30 July 2026); OpenAI cyber models broke out of a training environment to hack Hugging Face (CNBC, 22 July 2026); Australia’s Prime Minister said OpenAI hacked a Medicare portal (ABC News, 24 September 2026); and Replit’s coding agent deleted a user’s production database (The Register, 21 July 2025). The first three involved frontier models in evaluations with safeguards reduced or off; the last was a commercial tool given too much access. The lesson for a research workstation is the same: limit what the agent can reach.

Keep the working surface small

  • Provide power and a reliable internet connection. Keep the workstation running and reachable while you use it remotely. [5]
  • Create a dedicated user account without administrator rights. Keep personal credentials out; add only the scoped provider and project logins the agent needs.
  • Close outbound SSH from that account. The one exception: the login node of a cluster you have chosen to let it use (see Shared HPC). Blocking port 22 is a speed bump, not a full sandbox; do not treat a port rule as a complete security boundary.
  • Keep normal HTTPS available for package installs and provider access. SSH from your laptop to the workstation is useful for setup and maintenance, but not necessary.

Size for the work

Claude Code documents a 4 GB+ RAM baseline. The reviewed T3 documentation does not publish a combined minimum for T3, the harness and your project tools. [4]

As starting advice, consider at least 8 GB, with 16 GB comfortable for a modest workload, then size for your builds, browsers, datasets and concurrent agents. This is advice, not a T3 requirement or a measured capacity guarantee.

For the background-service recipe below, Linux needs systemd user services. Setup enables lingering so the service can start at boot and survive logout; follow its recovery instructions if administrator permission is needed. [6]

Sandbox recipe

Lock the box before the agent moves in.

A concrete version of the advice above for Ubuntu, run once from your own administrator account. Replace agent with the account name you choose and 192.0.2.10 with your cluster login node’s address.

  1. A dedicated account without sudo

    Lingering lets T3’s background service start at boot and keep running after you log out. [6]

    sudo adduser --disabled-password --comment "" agent
sudo loginctl enable-linger agent

    Give the account a login route you control, for example your SSH public key in /home/agent/.ssh/authorized_keys. Do not add it to the sudo group.

  2. Close outbound SSH for that account

    An nftables table that rejects TCP port 22 from the agent account, except to one login node, and a unit that loads it at boot. Your own account is unaffected.

    sudo tee /etc/agent-egress.nft >/dev/null <<'EOF'
table inet agent_egress
delete table inet agent_egress
table inet agent_egress {
  chain out {
    type filter hook output priority 0; policy accept;
    meta skuid "agent" tcp dport 22 ip daddr 192.0.2.10 accept
    meta skuid "agent" tcp dport 22 reject with tcp reset
  }
}
EOF
sudo tee /etc/systemd/system/agent-egress.service >/dev/null <<'EOF'
[Unit]
Description=Close outbound SSH for the agent account
DefaultDependencies=no
Before=network-pre.target
Wants=network-pre.target

[Service]
Type=oneshot
ExecStart=/usr/sbin/nft -f /etc/agent-egress.nft
RemainAfterExit=yes

[Install]
WantedBy=sysinit.target
EOF
sudo systemctl daemon-reload
sudo systemctl enable --now agent-egress.service

    The unit loads the rule before networking starts, as a host firewall does. No cluster? Delete the accept line. The rule matches an address, so update it if the login node’s address changes. After the next reboot, check that sudo nft list table inet agent_egress still shows the rule.

  3. Refuse inbound connections

    T3 Connect needs no inbound port, so the default is to deny everything. First list any rules already there and delete those you no longer need, since they stay open after enable:

    sudo ufw status numbered
sudo ufw default deny incoming
sudo ufw enable

    If you manage the box over SSH, allow that first, before ufw enable: check its port with ss -ltn, allow only the network you connect from (for example sudo ufw allow from 192.168.1.0/24 to any port 22 proto tcp), and confirm a second SSH login works before you close the current one.

  4. Cap memory and CPU for the account

    A runaway build or simulation then cannot starve the machine. Adjust the numbers to your hardware; 300% means three cores.

    sudo systemctl set-property "user-$(id -u agent).slice" MemoryMax=75% CPUQuota=300%

  5. Inside the account: scoped logins only

    • No personal SSH keys, password manager, browser profile or synced cloud folders. No mounted shared drives with data the agent should not change.
    • For GitHub, a fine-grained token limited to the repositories the agent works on, over HTTPS. For a cluster, a key used only for that login node; it still opens an ordinary shell there (see Shared HPC).
    • When you link it with T3 Connect, turn on Require approval for new devices, so a stolen T3 account alone does not reach the machine. [15]
    • Keep the system updated (Ubuntu installs security updates automatically by default) and update T3 with t3 update.

  6. Check it from the agent account

    id -nG                         # no sudo, admin or wheel
ssh -T git@github.com          # should be refused on port 22
curl -sI https://github.com    # should work

What this does not do. The agent can still read and change everything its account can, use HTTPS freely and reach SSH servers listening on other ports. Prompts and code still go to the model provider. Inside this box you can give the agent full access: the machine is the boundary, which is why it should not be your laptop or main computer. Keep anything irreplaceable off it, or backed up elsewhere.

Checked on 19 November 2026 in a fresh Ubuntu 26.04 virtual machine: the agent account could not use sudo, was refused on port 22 while the administrator account was not, kept HTTPS, and could install T3 Code and start its T3 Connect sign-in under these rules. Linking that machine was not part of the check.

Install & connect

Install on the workstation. Control from your laptop.

Do it yourself, or let an agent you have already installed on the workstation do it for you. Either way, finish the sandbox recipe first. The same is possible with VS Code’s remote development, just more tedious: VS Code is built for writing code, T3 Code for running agents.

Human version

  1. Install T3 on the Linux workstation

    Log in as the agent account. Download the installer, read it, then run it. It needs no sudo, checks the download against the release checksums and puts t3 in ~/.local/bin. On Ubuntu, a new login shell adds that folder to your PATH once it exists; otherwise follow the installer’s PATH instructions. [7]

    curl -fsSL https://t3.codes/install.sh -o t3-install.sh
less t3-install.sh
sh t3-install.sh

  2. Start the server and choose T3 Connect

    t3 up --connect

    Plain t3 up asks how other devices should reach the machine; --connect answers T3 Connect. Over SSH, or with no terminal, it prints a sign-in link and a short code: open the link on another device, check the code and approve. Connect runs T3 as a background service. [5] [15]

    As soon as your laptop is connected (step 5), turn on Require approval for new devices for this machine in Settings → Sharing & access, then review the devices it already trusts: on the workstation, t3 auth connect-device list shows them, and t3 auth connect-device revoke <code> removes any you do not recognise. [15]

    Check the environment and service state: [6]

    t3 service status
t3 connect status

  3. Install and authenticate your agent there

    Use the agent’s official installation guide, then run the matching login command on the workstation before starting a thread. Choose the provider you intend to use. [3]

    Claude Code, once installed

    claude auth login

    Codex CLI, once installed

    codex login --device-auth

    Codex’s device-code login must first be enabled in your ChatGPT security settings, or by your workspace administrator. [18]

    T3’s Codex provider also offers Connect with ChatGPT, including installation, on the selected remote environment. [3]

  4. Install the laptop client, or use the web app

    Choose one route from the official downloads. [7]

    macOS

    brew install --cask t3-code

    Windows

    winget install T3Tools.T3Code

    Debian / Ubuntu desktop

    Download the matching release .deb, then:

    sudo apt install ./T3-Code-*.deb

    Browser

    Open app.t3.codes. No desktop installation is needed. [7]

  5. Sign into the same Connect account

    In the laptop client, sign into the same account used on the workstation and select that environment. Agent installation and provider authentication belong to the selected workstation. [5] [3]

Agent version

  1. Install one agent by hand

    Log in to the workstation as the agent account, install Claude Code or the Codex CLI with its official installer, open a new login shell, and sign in. Both sign-ins print a link you can open on your laptop. [3] [18]

    Claude Code

    curl -fsSL https://claude.ai/install.sh | bash
claude auth login

    Codex CLI

    curl -fsSL https://chatgpt.com/codex/install.sh | sh
codex login --device-auth

    For Codex, enable device-code login in your ChatGPT security settings first, or ask your workspace administrator to.

  2. Paste this prompt

    Start the agent in the account’s home folder and give it this prompt. It installs and links T3 Code, checks the sandbox and shows you each sign-in link to approve. It does not use sudo; anything that needs it comes back to you.

    Set up T3 Code on this Linux machine so I can control you from my laptop. Follow the "Install & connect" section of https://comphy-lab.org/agents-in-research/ and T3 Code's own guide, https://github.com/pingdotgg/t3code/blob/main/docs/user/install.md.

Ground rules: work only as this user. Do not use sudo, and do not change the firewall, user accounts, SSH keys or system packages. If a step needs any of that, stop and give me the exact command to run myself. Tell me what each command does before you run it.

1. Check the machine: OS, CPU architecture, RAM, free disk, and that systemd user services run for this user with lingering on (systemctl --user is-system-running; loginctl show-user "$USER" -p Linger).
2. Check the sandbox and report each result: "id -nG" should not include sudo, admin or wheel; "ssh -T -o ConnectTimeout=10 git@github.com" should be refused; "curl -sI https://github.com" should work. List any private keys in ~/.ssh. If any check fails or is unclear, stop here and tell me; do not install anything.
3. Download https://t3.codes/install.sh to a file, read it, tell me in three lines what it does, then run it with sh. Check that "t3 --version" works; if t3 is not on PATH, use ~/.local/bin/t3.
4. Start T3 Connect in the background so you can read its output while it waits: t3 up --connect --headless > ~/t3-up.log 2>&1 &. Read the log every few seconds for up to 12 minutes, and watch the background job. Three outcomes: (a) a sign-in link and code appear: show me both exactly, then wait while I approve it on my laptop; the code expires after 10 minutes, and if the log then shows a timeout, run this step again for a fresh code. (b) It finishes without a code because this machine is already signed in: say so and go on. (c) It exits with an error: show me the last lines of the log and stop.
5. Run "t3 service status" and "t3 connect status" and report both; the second checks whether other devices can reach this machine. Go on only if the service is running and T3 Connect is reported reachable. If it is reported unreachable, wait a minute and check again; if it still is, show me the recovery message the CLI prints and stop.
6. Report which agent CLIs T3 Code will find on PATH (claude, codex) and whether each is signed in.
7. Tell me what to do on my laptop to connect. Then ask me to turn on "Require approval for new devices" for this machine (Settings, Sharing & access). When I confirm it is on, run "t3 auth connect-device list" and show me every trusted device, so I can revoke any I do not recognise with "t3 auth connect-device revoke <code>".

  3. Approve, then connect from your laptop

    Approve the T3 Connect link the agent shows you, then follow steps 4 and 5 of the human version on your laptop.

Documentation scope: T3 main-branch snapshot b78914e, reviewed 17 November 2026, with the scripted-setup and device-approval details from c4dc9ed, reviewed 19 November 2026. The install and sign-in commands were checked with T3 Code 0.1.10; the agent prompt has not yet been tested end to end.

Remote access

Remote control has a route.

Separate where commands execute from how prompts and approvals reach that machine.

Control paths described by the official sources
ConnectionExecution and message path
Claude Remote ControlClaude Code runs on your machine. Anthropic routes messages between clients and the local session through its API over TLS; the synchronised transcript, including tool activity, is stored on Anthropic servers. [9]
ChatGPT / Codex remote connectionsThe mobile/desktop remote-control route is vendor-mediated: the phone sends prompts and approvals to ChatGPT while commands execute on the connected, awake Mac or Windows host. The cited guide describes a secure relay but does not establish every network hop or a complete retention policy. [9]
Codex SSH / CloudSSH is a separate route: the desktop app manages a remote Codex App Server through SSH. Codex Cloud instead executes tasks on OpenAI-managed computers. Do not apply the mobile relay description to both. [9] [10]
T3 ConnectAgents run on your workstation. T3-managed Cloudflare tunnels carry application traffic. A T3 relay provisions and discovers endpoints and brokers credentials; ordinary HTTP/WebSocket traffic uses the environment’s tunnel hostname rather than passing through the relay Worker. [8]

Managed Connect

Free for now, for up to three linked machines per account. Phones and browsers do not count towards that allowance. This is the documented offer as of 17 November 2026. [5]

Your own Connect infrastructure

The source and runbooks support an operator deployment using your own Cloudflare, Clerk, database and related services, plus client configuration or rebuilding. The reviewed docs do not provide a turnkey, entirely independent Linux-only setup. [12]

The tunnel does not move inference onto your workstation. Whatever connection you choose, prompts and code still go from the workstation to the selected model provider. [8]

Subscriptions & API

Subscription or pay per token?

A subscription buys plan access

Subscriptions can be much cheaper for heavy interactive use than pricing the same recorded tokens at API list rates. That comparison is an estimate, not a guaranteed API allowance or a measure of the provider’s compute cost. OpenAI explicitly separates API token prices from subscription usage. [11] [13]

The API bills usage

API list prices charge input and output tokens separately. Cache accounting, tools and service tiers can change the bill. Compare against the provider’s current rates and your actual workload. [11]

Some plans also include claimable API credits under separate rules; for example, Claude Max and Ultra document these allowances. Do not confuse those credits with an API-equivalent estimate of subscription use. [14]

Skills & AGENTS.md

Write the know-how down once.

Skills

A skill is a folder of instructions the agent loads only when a task needs it. You write it once and every agent that supports skills can reuse it. [16] The talk’s demo prompt names seven:

basilisk-master
Basilisk solver know-how: sources, APIs, build errors.
basilisk-runs
Preflight, launch, monitor and close out simulations.
publication-plots
Consistent, publication-quality figures and videos.
research-compute-dispatch
Reserve compute; never disturb other runs.
council-of-sages
Two independent AI reviewers must approve.
gh-pr-create
Open a pull request with a clear description.
full-stop
Finish the work, stop at the open pull request: a human merges.

Sanitised public versions are published, as they become ready, in rayleigh-coding. In T3 Code a prompt names a skill as $name; in Claude Code’s own interfaces it is /name.

AGENTS.md

Standing rules every session reads first: how the project works, what to do, and what never to do. Codex reads AGENTS.md. Recent Claude Code versions read it too when a project has no CLAUDE.md; otherwise a CLAUDE.md can import it with a single line, @AGENTS.md. [17]

In my experience, aligned models follow these rules closely. Still, they guide; they do not enforce. Enforcement is the sandbox’s job.

Shared HPC

Keep shared HPC behind a narrow door.

Recommended practice, for people who do not trust LLMs: prepare the submission package locally, then let the agent run only small submit and status scripts you have read and approved. Give it only the permissions those steps need, within your centre’s policies.

  1. Prepare: review the code, job script, inputs and requested resources.
  2. Submit: use the approved script for the intended job and record the scheduler job ID.
  3. Poll: read status and logs for that job. Automatic polling, and a bounded resubmission if a job fails, are optional; keep them appropriate for the service.

Allow outbound SSH to that one login node only (the exception in the sandbox recipe). SSH alone would give the agent a general shell on a shared machine. Restrict it with the harness’s command allowlist and keep the approved scripts read-only to the agent, but treat that as a guard rail: the key itself still grants your full cluster account. Where your centre supports it, use a restricted key (a forced command in authorized_keys) or a site-approved submission service instead.

The full scripts are public: VatsalSy/agentic-hpc-scripts. They submit through SLURM, check that the scheduler really returned a job ID, poll, and bound resubmission, with mocked tests. Read them and adapt them to your cluster before use.

The demo

One prompt, one paper, one pull request.

The prompt fired at the start of the talk, word for word except for the workstation’s name and the reservation details. Its inputs are a public paper, “Impacting spheres: from liquid drops to elastic beads” (Soft Matter, 2026), and its public code, comphy-lab/Soft-Sphere-Impacts. The words starting with $ are skills.

Look at this paper: "Impacting spheres: from liquid drops to elastic beads" (Soft Matter 2026), PDF attached. The source code is github.com/comphy-lab/Soft-Sphere-Impacts. Clone it and follow its AGENTS.md.

Clock: record `date -u` now and at each milestone; report the total at the end.

1. Reproduce Figure 5(a). Use $basilisk-master and $basilisk-runs. Simulate the infinite-Weissenberg (Kelvin–Voigt) case, bounce-kv.c, at We = 100 and El = 40 (Ec = 4000), at grid level 9: coarse, but enough for a first comparison. Digitise F(t) from Figure 5(a) and compare the two with $publication-plots, stating the relative error in F_max and in its time. Add a drop-impact video coloured by velocity.

2. In parallel, find the Bingham (viscoplastic) model in github.com/comphy-lab/MultiRheoFlow and implement it here: twoPhase-VP.h with the plumbing it needs, and bounce-bingham.c, following the existing drivers. Run one Bingham case at We = 100 with yield stress J = τ_y/(ρV²) = 0.001 and add its F(t) to the plot.

3. Fully document bounce-kv.c, the driver behind the soft-matter paper. Be concise and to the point.

4. Combine everything on one branch. Get $council-of-sages approval (seats gpt-6.2-astra at medium effort and claude-fable-5-2 at high; two rounds are enough if both seats score above 7), then $gh-pr-create a normal PR. $full-stop: never merge.

Rules: simulations through $research-compute-dispatch on <workstation>, inside my published reservation <reservation> (8 cores, 32 GiB). I authorise running while it stays held: give each run half its cores, 4 threads each; skip activation, tracker updates and release, and book nothing else. If it is unavailable, you may stop one of my lower-priority simulations, never a registered or production run, and record exactly what you stopped. The PR carries code and documentation only (it is public). Report the plot, the video, the PR link and the timings.

A caveat in the prompt. Figure 5(a) plots force against t/tmax, the time scaled by the time of the first force peak, so the paper’s peak sits at 1 by construction. The figure alone therefore tests the peak force and the curve’s shape well, but not the peak time; that needs an independent reference time.

The rehearsal’s pull request

A run of this task the night before the talk opened Soft-Sphere-Impacts #6, adding a Bingham drop-impact driver. It was reviewed by two AI reviewers and left open: a human merges.

A longer collaboration

One exchange with a simulation agent on a running parameter study, shown in full: the instructions it works under, two scheduled checks and the shapes it drew.

What this page did not cover: ask your agent. Ask it to talk you through things, as you would a PhD student. If it does something surprising, ask it to explain step by step: assumptions, derivation, and a check you can run. Delegating to an agent does not delegate the responsibility.
